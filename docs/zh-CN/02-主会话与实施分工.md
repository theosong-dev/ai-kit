# 主会话与实施分工:规划、派单、验收分开做

[English](../02-main-session-and-implementers.md) | 简体中文

做法一句话:**主会话只做规划、派单、验收,实施交给 subagent,验收交给另一个不带实施历史的 subagent。**

## 为什么要分

**主会话的上下文留给判断。** 实施过程会产生大量读文件、跑命令、改代码的中间输出。全部堆在主会话里,上下文很快被细节占满,后面做方向判断时反而看不清。实施放进 subagent,主会话只拿回结论。

**实施者的自述不可信。** 写代码的 agent 说「已测试通过」「没问题」,并不等于真的通过。这不是态度问题,而是同一个上下文里的人很难找出自己的盲点。所以验收必须由另一个 agent 来做,而且不能让它看到实施过程,以免顺着实施者的思路走。

## 派单

### 派单前先写隐含假设与 edge case

在写派单之前,主会话先列出这次改动依赖的隐含假设(比如「这个字段一定非空」「这个接口只在登录后调用」)和可能的 edge case。很多返工不是实施者能力不够,而是这些东西只存在于主会话脑子里,派单里没写。

### 五要素

1. **Intent**:要达成什么,为什么做。
2. **改哪些文件,按什么顺序。**
3. **可执行的验收标准**:能跑的命令、能观察的行为,而不是「功能正常」。
4. **约束与风险**:不能动什么、哪里容易出错。
5. **参考文件**:相关实现、类似的已有代码。

检验标准:**一个没看过这段对话的人,能凭这份派单单独完成实施。** 做不到,说明派单还缺东西。

## 按 effort 分档的四个实施 agent

effort 只能写在 agent 文件的 frontmatter 里,派单时无法临时指定,所以按档位拆成多个 agent,派单时选名字:

| agent | 模型 / effort | 适用 |
|---|---|---|
| `sonnet-implementer` | sonnet / medium | 方案完全明确、单文件或少量文件的机械任务 |
| `opus-implementer` | opus / medium | 方案清楚但跨文件、需读较多上下文的常规实施。拿不准时用这个 |
| `opus-implementer-high` | opus / high | 方案留有判断空间、需权衡实现路径、改错代价较高 |
| `opus-implementer-xhigh` | opus / xhigh | 非显而易见的 bug、并发 / 一致性问题、核心路径重构 |

### 选档看什么

effort 买的是**验证量和 edge case 覆盖**,治不了方向错。所以选档看两件事:**隐藏的 edge case 多不多,改错代价高不高**;不看任务大小。一个改动很大但纯机械的迁移,用低档就够;一个三行的并发修复,可能要最高档。

### 升档之前先给自检手段

在想升档之前,先在派单里给实施者一个自检手段:能跑的测试、构建或命令。**一次检查只花一轮,升档是每轮都多想。** 大多数「低档做不好」的情况,是因为实施者没有办法知道自己做错了,而不是想得不够多。

### 失败两次就回主会话

同一个问题失败两次,回到主会话重新定方案,而不是再加一档。两次都没做对,通常说明方案本身有问题,加档只会更认真地执行错的方案。

## 独立 verifier

实施 agent 返回后,主会话派 `verifier` 验收。它的设计:

- **只读**,不改任何文件。
- **不带实施历史**,只拿三样东西:派单原文、待验收的 diff / 文件、验收标准。
- **立场是找证据推翻「已完成」**,而不是确认它。实施者说「已测试通过」不作数,verifier 没有亲自跑出来的,就是 UNVERIFIED,不是 PASS。
- 对每条验收标准亲自执行对应命令或观察对应行为,逐条给 **PASS / FAIL / UNVERIFIED**;UNVERIFIED 必须说明为什么无法验证。
- 发现的问题带类别标签,便于后续统计哪类问题反复出现(参见 `01-双层记忆循环.md` 里 `/distill` 的输入)。
- 实施 → 验收最多 3 轮。超过就回主会话重新看方案。

## 不得基于 mock 报完成

单测通过不等于功能可用,尤其当测试 mock 掉了外部依赖时。规则是:

- 改动涉及 **LLM / 外部 API / 数据库**,必须走一次真实路径;只跑了 mock 或 fake provider 不算数。跑不了就标 UNVERIFIED 并说明缺什么。
- **用户可见的界面改动**,要在浏览器里实际走通,有截图或页面文本作为证据。
- 报完成时**列出做了哪些验证、哪些没做**。没做的验证写明原因,而不是不提。

一个真实的例子:给某个插件加一项记录功能时,代码依赖宿主提供的一个列表 API 来查询 subagent 的类型。类型声明看起来没问题,单测 mock 了这个 API,10 个用例全部通过。但用真实命令跑一次后,日志里一条记录都没有。加诊断输出才发现,这个 API 在真实运行时返回空数组,根本不包含由 Agent 工具派出的 subagent。mock 返回的是「声明上应该有的数据」,而真实环境给的是另一回事。这个问题只有冒烟运行才能发现。之后的约定是:这类插件改动不以 mock 单测为准,派单里必须带一条真实运行的验收命令。

## 在本仓库里怎么用

- `claude/agents/`:四个实施 agent(`sonnet-implementer.md`、`opus-implementer.md`、`opus-implementer-high.md`、`opus-implementer-xhigh.md`)和 `verifier.md`。复制到 `~/.claude/agents/` 即可在 Claude Code 里按名字派单。
- 实施 agent 正文里约定了固定的返回格式:改动文件列表、验证命令与原始输出关键行、偏离派单之处、未做与原因、考虑过但没采用的做法。这让主会话不必重读实施过程,也给 verifier 提供了可以逐条核对的东西。
- 主会话本身用较低的 effort 也可以,因为它只做规划和判断,重活都在 subagent 里。

## 局限

- 分档的边界是经验判断,没有做过同一任务在不同档位下的系统对照。
- verifier 的类别标签统计依赖信号日志积累,目前数据还少。
