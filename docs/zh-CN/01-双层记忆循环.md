# 双层记忆循环:项目记忆怎么不丢、不膨胀、变成规则

[English](../01-two-loop-memory.md) | 简体中文

AI coding agent 每次会话都从零开始。不写进文件的进度,下次会话就丢了;但什么都往文件里堆,文件又会在每次会话开头吃掉上下文。这里的做法是把记忆分成两层循环:

- **内层(`/wrap`)**:每次会话收尾时,如实记录发生了什么。
- **外层(`/distill`)**:攒够了经验之后,把重复或高代价的那部分升成一条可复用规则,放进正确的加载通道。

内层只负责「记」,外层只负责「改」。两件事分开,是为了让收尾足够轻,轻到每次都愿意做。

## 内层:三个文件

每个项目根目录下放一个 `.ai/`,里面三个文件:

| 文件 | 记什么 | 写法 |
|---|---|---|
| `PROGRESS.md` | 当前状态、下一步、遗留问题、任务清单、进度日志、「用户纠正(待蒸馏)」 | 可改,有体积上限 |
| `DECISIONS.md` | 重要决策:背景、选了什么、放弃的备选、原因 | 只增不改 |
| `GOTCHAS.md` | 踩过的坑:试了什么、为什么失败、以后怎么做 | 只增不改 |

项目的 `AGENTS.md` 里写明「开始工作前先读 `.ai/PROGRESS.md`」,`DECISIONS.md` 和 `GOTCHAS.md` 相关时再读。这样一个新会话几秒内就能恢复状态,而不必读完全部历史。

`DECISIONS.md` 和 `GOTCHAS.md` 只增不改,是因为它们是证据:之后蒸馏规则时,要能指回「当时到底发生了什么」。改写过的历史就不能当证据用了。

### 为什么 PROGRESS 要有硬上限

`PROGRESS.md` 是唯一一个**每次会话开头都会读**的文件,它的每一行都直接占用上下文。决策和坑可以按需读,进度不行。所以 `PROGRESS.md` 要有硬上限,超出的部分归档。

上限不靠目测。「看起来还不长」这种判断每次都会放宽一点,最后文件就会膨胀。`/wrap` 会跑一个检查脚本(`check_size.sh`),上限值、段名规则、各项 OK / OVER 的判据都写在脚本里,skill 正文不复述。

### `/wrap` 做什么

会话收尾时触发(「收尾」「更新进度」「wrap up」),按顺序:

1. 刷新「当前状态 / 下一步 / 遗留」。
2. 勾选任务清单里**已端到端验证**的项;没验证的不勾。代码写完不等于完成。
3. 进度日志加一行。
4. 本次有决策或踩坑,追加到 `DECISIONS.md` / `GOTCHAS.md`。
5. 用户在本次会话里纠正过 agent 的做法,记到 PROGRESS 的「用户纠正(待蒸馏)」段。纠正是规则最好的原料,不记下来就没了。
6. 跑 `check_size.sh`。任一项 OVER:超出的进度日志条目原文追加到 `.ai/archive/PROGRESS-YYYY-MM.md`,本文件只留压缩后的一行;「当前状态」超行就压缩,但保留警示状态(未 push / 未验证 / 严禁发版),去掉实现细节。归档后再跑一次脚本,确认 exit 0。

## 外层:`/distill` 把经验升成规则

内层记下的东西大多不该变成规则。规则越多,每条被遵守的概率越低。`/distill` 的工作是筛选、分流,并且做减法。

### 进入门槛

输入由脚本收集,不靠肉眼:`pending.sh` 列出未蒸馏的 GOTCHAS / DECISIONS 条目和「用户纠正(待蒸馏)」,并给出标题重复线索;`signals.sh` 从信号日志里找跨 ≥2 个会话重复出现的同类工具失败。两类线索都只是线索,仍要人工再核一遍。

候选必须满足其一:

- 同一问题**重复出现 ≥2 次**;
- 或单次**代价很高**(数据丢失、发错版、安全边界、动了生产数据)。

并且每条候选必须写得出一句「**本可防住哪次真实错误**」。写不出来的,说明它是预防想象中的问题,不升。

### 按加载通道分流

同一条经验,放在不同位置,被执行的方式完全不同。分流依据是「它需要以什么方式生效」:

| 经验的形态 | 落点 |
|---|---|
| 每次 X 都要发生 Y | hook(由宿主执行,不依赖模型记得) |
| 禁止做 X | 权限配置 / PreToolUse 拦截 |
| 多步流程,特定场景才需要 | skill(按需加载) |
| 每次会话都要知道的常驻事实 | `AGENTS.md` |

「每次 X 就 Y」写成提示词,模型某次忘了也不会报错;写成 hook 就不会忘。这一点在 `03-护栏机制化.md` 里展开。

### 减法

每次蒸馏都要同时看能删什么:被新规则覆盖的旧规则、已经被机制(hook / 权限)接管的文字规则、从没起过作用的规则。删除同样需要用户批准。

### 规则带来由

新增或修改的规则,在同一行末尾带一句来由:年月、来源(哪条 GOTCHAS / DECISIONS、哪天的用户纠正,或「信号日志 N 会话 M 次」)、执行本次蒸馏的模型名。

带模型名是为了换模型后复查:很多规则是在补偿某一代模型的行为缺陷,换了模型可能就不再需要。`/distill` 会把「来由里的模型名与当前模型不同」以及「没有来由、看起来在补偿模型缺陷」的规则列进待复查清单。复查不等于删除。

### 未批准不落地

`/distill` 的产出是**最小 diff 提案**,每条写明:来源条目 → 加 / 改 / 删的原文 → 落点通道 → 本可防住的真实错误 → 一句验证方法(跑什么命令、应得什么结果)。用户批准的范围内才落地,范围外的一律不动。

## 没验证过的 / 目前的局限

- **换模型复查还没有真正做过。** 来由里的模型名已经在记,但还没经历过一次「换模型后按清单复查、删掉过时规则」的完整流程,这一步的效果目前是设想。
- **信号统计数据还少。** `signals.sh` 依赖信号日志积累;日志时间短时,「跨会话重复」的线索很稀疏,门槛判断主要还是靠 GOTCHAS 和用户纠正。
- 体积上限的具体数值是经验值,没有做过「上限多少最合适」的对照。

## 在本仓库里怎么用

- `templates/project/`:项目记忆模板,复制到你的项目根目录。
- `skills/wrap/`:`/wrap` 的正文和 `check_size.sh`。
- `skills/distill/`:`/distill` 的正文和 `pending.sh` / `signals.sh`。
- `mods/`:其中的信号记录 mod 为 `signals.sh` 提供日志来源。

两个 skill 的脚本都按 `SKILL.md` 所在目录定位,并显式传入目标项目根,不依赖当前工作目录或宿主注入的环境变量,所以 Claude Code 和 Codex 可以共用同一份。
