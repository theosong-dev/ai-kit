# 信号日志与验收统计

## 问题

逐单验收(每次实施完派一个 verifier)能挡住这一单的错，但看不出另一类问题：多个 agent 在不同会话里反复犯同一类错，或者反复走同一条捷径。例如同一条命令在五个会话里以同样的方式失败，或者实施者一再「只跑了 mock 就说已验证」。每一单单独看都只是个小问题，合在一起才是该改规则的信号。

这个思路来自 Lauren Tan 在 Matt Pocock 播客里讲的做法(经宝玉 @dotey 的总结)：抽查的目的是找重复模式，不是逐个 review。

## 做法

分两步，记录和统计各管一件事：

1. **记录**：一个 Claude Code mod `turn-signals` 在会话里旁听，往一个跨会话、跨账号的 JSONL 文件追加精简信号。它不显示任何东西，只写文件。
2. **统计**：`distill` skill 里的 `signals.sh` 读这个文件，做确定性统计，把「跨会话重复」的线索交给人或 agent 判断。

统计由脚本做，不让模型去「读日志找规律」：同样的输入总得到同样的分组，结果可以复查。脚本的输出是线索，不是判定，要不要据此改规则仍由人决定。

## 记录什么

默认写到 `~/.local/state/claude-insight/turn-signals.jsonl`，可用环境变量 `TURN_SIGNALS_PATH` 换路径。每条一行 JSON：

```json
{"type":"tool","kind":"error","ts":"…","session":"…","cwd":"…","account":"claude-2","tool":"Bash","subagent":false,"error":"Exit code 2\n…","command":"ls /nonexistent-dir-xyz"}
{"type":"turn","ts":"…","session":"…","cwd":"…","account":"claude-2","reason":"answer","durationMs":6134,"tools":1,"failures":1}
{"type":"interrupt","ts":"…","session":"…","cwd":"…","account":"claude-2","durationMs":900,"tools":1}
{"type":"verdict","ts":"…","session":"…","cwd":"…","account":"claude-2","agentId":"…","implementer":"opus-implementer","verdict":"FAIL","issues":[{"cat":"no-real-path","text":"…"}]}
```

- `tool`：工具失败或被拒。`kind` 为 `error`(跑了但报错)、`interrupted`(运行中被打断)、`refused`(根本没跑：权限规则、用户拒绝或 hook deny)。`error` 截前 200 字符，Bash 另记 `command` 前 120 字符；subagent 里的调用带 `subagent: true` 和 `agentId`。
- `turn`：主循环每轮一条摘要，`reason` 是 `answer` / `aborted` / `refusal` / `error`。
- `interrupt`：用户按 Esc 中断整轮时多记一条。
- `verdict`：类型名为 `verifier` 的 subagent 每结束一轮记一条。取回答里最后一处 `VERDICT: PASS|PASS-WITH-NOTES|FAIL`，没有就记 `UNKNOWN`；`issues` 取形如 `- [slug] 正文` 的行，最多 12 条。`implementer` 是本会话里在这个 verifier 之前启动的最近一个非 verifier subagent 的类型名。

写文件用 `/bin/sh` 的 `mkdir -p` 加 `cat >>`(O_APPEND)，两个会话同时写不会互相覆盖。写失败只进 debug 日志，不影响会话。

## verifier 的问题类别

为了让验收结论可以统计，verifier 的提示词要求每条问题以一个类别标签开头，从下表选一个：

| slug | 含义 |
| --- | --- |
| `no-real-path` | 只跑了 mock / fake / 读代码，没有真实 provider 或浏览器走通的证据 |
| `criteria-fail` | 某条验收标准对应的行为实际不成立 |
| `test-fail` | 项目已有 test / build / lint 失败 |
| `out-of-scope` | 改了派单没要求的文件或行为 |
| `uncommitted` | 未提交或未推到派单要求的位置 |
| `false-claim` | 实施者自述(已测试 / 已验证 / 已完成某项)被 verifier 跑出的结果推翻 |
| `other` | 以上都不是 |

一条问题只打一个最贴切的标签；同时符合 `false-claim` 和其他类时优先 `false-claim`。不在表里的 slug 记为 `other`。

## 统计怎么做

```bash
bash signals.sh <PROJECT_ROOT> [--days N]      # 默认最近 30 天，只读
```

工具失败部分：

- 只取 `cwd` 在项目根之下、在时间窗口内的 `tool` 行。
- 按签名分组：工具 + `kind` + Bash 命令头 + 归一化后的错误首行。归一化把引号内容、URL、uuid、路径、长十六进制串和数字替换成占位符，再截前 80 字符，让「同类错误、不同参数」落进一组。Bash 命令头会去掉 `cd X &&`、环境变量赋值、`sudo` 这类前缀，常见子命令(如 `git push`、`npm run`)一并计入。
- **只输出出现在 ≥2 个不同 session 的组**。同一会话里重复多少次都只算 1，因为会话内的重试不说明有跨会话的模式。

verifier 部分：

- 先打结论分布(各 verdict 的条数、会话数)。
- 再按 `issues[].cat` 分组，每组给条数、会话数、首末日期、按 `implementer` 计数和最多 3 条样例。会话数 ≥2 的组标 ★，作为进入 distill 的门槛。

脚本在注释里写明了已知局限：误并(只有 `Exit code N` 的失败会按命令头合在一起)、误分(措辞随参数变化的同类错误会拆成几组)、含 `/` 的普通词会被当成路径抹掉。这也是输出只算线索的原因。

## 怎么加载

mod 是纯 `.mjs` 的 function hooks 模块，以 plugin 形式打包，没有 npm 依赖。试用时只对本次会话生效，不安装：

```bash
claude --plugin-dir <ai-kit>/mods                  # 加载目录下所有 mod
claude --plugin-dir <ai-kit>/mods/turn-signals     # 只加载一个
```

日常使用可以把 `--plugin-dir` 加到启动 alias 上。绕过 alias 启动的会话(如桌面端)不会加载。

同目录下另一个 mod `token-weather` 在输入框上方显示上下文占用(图标 + 百分比 + 最近几轮的 sparkline)，和信号日志无关。

## 踩过的坑

**`$.agent.list()` 查不到 Agent 工具派出的 subagent。** 加 verdict 记录时，最初在 subagent 的 `turn.complete` 里用 `$.agent.list()` 按 `agentId` 找类型名，类型声明里也写着 `AgentInfo.type`。真实运行时它返回空数组。现在的做法：类型名从 `classic.SubagentStart` / `classic.SubagentStop` 的 `agent_type` 记进 `$.state`；回答文本取 subagent 的 `turn.complete` 的 `answer`(`SubagentStop` 的 `last_assistant_message` 实测为空)。

**mock 单测全过，真实运行不写行。** 上面那个问题，mock 了 `agent.list` 的 10 个单测全部通过，是用 `claude -p` 真实派一次 verifier、发现日志里没有 verdict 行才暴露的。结论：mod 改动不以 mock 单测为准，必须带一条 `claude -p` 真实冒烟。这也正是 `no-real-path` 这个类别要抓的情况。

## 已知限制

- **数据还很少**：日志才攒了几天，目前还没有从统计里得出过任何结论。这套东西有没有用，要等数据攒够再看。
- **账号标识是推断的**：plugin API 不提供账号信息，取 `CLAUDE_CONFIG_DIR` 最后一段并去掉开头的点(`~/.claude-2` 记为 `claude-2`)，没设就是 `claude`。
- **`refused` 分不清是哪种拒绝**：区分「失败」和「被拒」靠观察推出——工具真跑了又失败时引擎会先发 `classic.PostToolUseFailure`，被拒时不发。所以权限规则、用户点拒绝、hook deny 都落进 `refused`。输入校验失败这类情况推测也落进 `refused`，未验证；用户在交互界面点拒绝这一条也没有实测。
- **看不到是哪条规则拒绝的**：`tool.check` 只在弹窗决定之前触发，看不到用户最后的选择，所以没用它。
- **中断只认整轮**：只认整轮以 `aborted` 结束的情况；单个工具被打断记作 `kind: "interrupted"`。
- **verdict 匹配较宽松**：`VERDICT:` 的匹配没有词边界(`VERDICT: PASSED` 会记成 PASS)。`implementer` 不区分是谁启动的，mod 加载之前启动的 subagent 不计入。
- **`claude -p` 下照常工作**：失败记录、拒绝记录、轮摘要和 verdict 行都实测写出过。
- **热重载安全**：每次重载会重跑 `register` 和 `session.start`；`turn-signals` 在 `session.start` 里不写任何东西，重载不会产生重复行。
