# 护栏机制化:能用机制拦的,不写成提示词规则

## 核心判断

提示词里的规则有一个根本问题:**没人执行时不会报错。** 模型某次忘了「提交前要跑测试」,不会有任何东西提醒你;你只会在后面某个时刻发现问题。而 hook、权限配置这些机制由宿主执行,不依赖模型记得。

所以先判断一条约束的形态,再决定放在哪里:

| 约束的形态 | 放在哪里 |
|---|---|
| 「每次 X 都要 Y」 | hook |
| 「禁止 X」 | 权限配置(`permissions.deny`)或 PreToolUse 拦截 |
| 需要判断才能执行的事 | 文字规则(`AGENTS.md` / skill) |

文字规则只留给真正需要判断的事。能写成「遇到 A 就做 B」的,基本都可以交给机制。

## `guard.sh`:PreToolUse 拦截

`guard.sh` 是一个全局的 PreToolUse hook。它从 stdin 读 hook JSON,对 Bash 命令做确定性判断;exit 2 拦下这次调用,并把 stderr 的说明返回给模型。

它拦这些:

- **向 main / master 强推。** `--force`、包含 `f` 的单横线参数簇(`-f`、`-uf`)、以 `+` 开头的 refspec 都算强推;`--force-with-lease` 不算。目标分支取显式 refspec 的目的端,没有时取当前分支。
- **跳过钩子**:git commit / push / merge 上的 `--no-verify`,以及 git commit 的 `-n`。
- **危险的递归删除**:目标是 `/`、`.`、`..`、`*`、`/*`、`~`、`$HOME` 或 git 仓库根。
- **递归删除 `.next` 构建目录**(含 `.next-` 前缀的变体),因为开发服务器可能正在用。
- **破坏性的 git 历史 / 工作区命令**:带 `--hard` 的 `git reset`,带 `--force` 或含 `f` 参数簇的 `git clean`。`git reset --soft`、`git clean -n`、`git stash` 等不拦。

几个设计取舍:

- 命令按未加引号的换行和 `&&` `||` `;` `|` 切成多段,每段单独判断;用 Python 的 `shlex` 分词,所以引号里的内容是一个参数,不参与匹配(`git commit -m "fix: handle -n flag"` 放行)。
- 每段都带一个「有效工作目录」:`cd <path>` 会影响后面的段,`git -C <path>` 只影响这一次调用。
- 解析不了的命令回退到按空白切分,定位不到仓库时没有显式 refspec 的强推直接拦——**不确定时偏向拦截**。
- 解析 hook JSON 失败时放行(fail-open),因为 `permissions.deny` 是第二层。

### 怎么测

`guard_test.sh` 把构造好的 hook JSON 喂给 `guard.sh`,断言退出码:

```bash
bash claude/hooks/guard_test.sh
```

改 `guard.sh` 之前先加一条会失败的用例,改完让它通过。拦截规则写错的代价是要么挡住正常工作,要么放过危险命令,两者都值得一条测试。

### 已知的误拦

`guard.sh` 按 argv token 扫描,不区分「要执行的命令」和「传给子进程或写进文件的字符串」。例如在 Bash 里用 `claude -p "...--no-verify..."` 做端到端测试,或用 heredoc 往文档里写一段提到这个参数的文字,都会被拦下。方向是误拦而不是误放,属于设计取舍。遇到时改用不经过 Bash 参数的方式(比如用文件编辑工具写文档)。

## `session-start.sh`:不依赖模型主动读

项目约定「开始工作前先读 `.ai/PROGRESS.md`」,但这仍是一条文字规则。`session-start.sh` 把它变成了 SessionStart hook:当前仓库有 `.ai/PROGRESS.md` 时,自动注入它的尾部 60 行,以及 `git status -sb` 和最近 5 条提交。没有 `.ai/` 的仓库直接退出,不产生输出。

## 权限放行的经验

- **需要长期放行的工具,走 `permissions.allow`。** allow 的判断先于自动分类器。不要靠改提示词措辞去绕过拦截,那样下次换个说法又会被拦。
- **被自动分类器稳定拦截的几类操作,不要先自己试。** 实践中稳定被拦的有:读写浏览器 cookie / 登录态 / 凭据同步;clone 并运行第三方代码、开 Chrome remote debugging;往用户级配置(如 shell 配置、全局 agent 规则目录)写入。遇到这几类,直接给用户一条可粘贴的命令让用户自己运行,并先读该工具的 `--help` 确认输入格式。反复试只会浪费轮次。
- **subagent 被拒后请主会话代做的,主会话不代做。** 一次拒绝是权限系统的决定,换一个执行者绕过去等于让拦截失效。正确的做法是把被拒的操作和原因报给用户。

## 纠正出现两次,按层级修

同一类纠正出现两次,就把它当成一类问题处理,而不是再口头提醒一次。修复按以下层级,能用上层的就不用下层:

1. **结构上消除**:让错误无法发生,比如删掉容易用错的接口、改目录结构。
2. **自动检查**:hook、lint、拦截脚本。报错信息里写明**应该用什么**,而不只是「不允许」,这样模型拿到报错就能自己改正。
3. **测试**:把这次错误写成一条会失败的用例。
4. **最后才是文档规则**:写进 `AGENTS.md` 或 skill。

这个层级和 `01-双层记忆循环.md` 里 `/distill` 的分流表是同一个思路:越往下越依赖模型自觉,越往上越不需要。

## 在本仓库里怎么用

- `claude/hooks/guard.sh`、`claude/hooks/guard_test.sh`:PreToolUse 拦截脚本及其测试。
- `claude/hooks/session-start.sh`:SessionStart 注入脚本。
- 把它们复制到 `~/.claude/hooks/`,并在 Claude Code 的 `settings.json` 里注册对应的 `PreToolUse`(matcher 为 `Bash`)和 `SessionStart` hook。
- `skills/distill/`:决定一条经验该落到 hook、权限还是文字规则时用。

## 局限

- `guard.sh` 只检查 Bash 命令,不覆盖其他工具的写操作;它是一层护栏,不是沙箱。
- 误拦问题目前靠绕开处理,没有做「区分命令与字符串内容」的改造。
